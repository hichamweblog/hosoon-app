> **حالة التنفيذ — 2 أكتوبر 2026:** نُفّذت T01–T25 محليًا مع اختيار الورد التقويمي المستقل P2-A. الخانات المنجزة تعني الكود والتحقق المحلي، لا نشر الإنتاج أو توثيقًا دينيًا/اختبار هواتف فعلية. النتائج والحدود في `IMPLEMENTATION_AR.md`، وبوابة النشر والتراجع في `DEPLOYMENT_AR.md`.

**الهدف:** تطبيق يحفظ تقدم المستخدم بأمان، ويقيس الحفظ فعلًا، ويوصل إلى جلسة يومية واضحة وسهلة، دون إعادة كتابة المشروع.

## 1. نطاق التنفيذ والتقدير

الخطة الأساسية: **8–10 أسابيع**، بافتراض مطور Full-stack متفرغ، ومصمم/QA بدوام جزئي، ومراجع متخصص بالمنهج وبيانات القرآن عند نقاط الاعتماد. هذا تقدير تخطيطي قابل للتعديل بعد تقدير المهام ومعرفة بيئة النشر، لا التزام زمني.

- **أول 1–2 أسبوع:** إصلاحات أمان وثقة عاجلة، مع اختبارات تمنع تكرارها.
- **الأسابيع 3–4:** ترسيخ المزامنة وعزل الحسابات وترحيل البيانات والنسخ الاحتياطي.
- **الأسابيع 5–6:** الجلسة والمصحف والنوافذ والوصول وإكمال التدفقات الناقصة.
- **الأسابيع 7–8:** هرمية الشاشة اليومية والصوت وoffline وإطلاق تجريبي؛ وقد تمتد إلى الأسبوع 10 للاختبار والإصلاحات.
- **بعدها، 2–4 أسابيع اختيارية:** فصل الورد التقويمي بالكامل، مراجعة علاجية أذكى، وإشعارات خلفية إذا أثبت الاستخدام الحاجة.

إذا كان الوقت أسبوعين فقط: نفذ إصدار الثقة الأول، وأجّل المزايا الجديدة. وإذا توفر مطوران يمكن العمل بالتوازي على البيانات/المزامنة والواجهات بعد تثبيت عقود البيانات، لا بدء إعادة تصميم شاملة قبلها.

### تعريف «تم» لأي مهمة

الكود + اختبار للمشكلة الأصلية + اختبار عدم فقد بيانات سابقة + حالة خطأ واضحة + تحقق هاتف/RTL + مراجعة عند الحاجة. لا يعتبر زر أو toast نجاحًا كافيًا لمسار حفظ أو مزامنة.

## 2. قرارات المنتج التي يجب حسمها أولًا

اجتماع قصير مع صاحب المنتج ومراجع المنهج، وتوثيق النتائج في يوم العمل الأول:

| القرار | التوصية الافتراضية |
|---|---|
| ما هو «ثمن محفوظ»؟ | `new_hifz` منجز أو محفوظ سابق صرّح به المستخدم؛ الاستماع/التحضير لا يثبتان الحفظ |
| ما هو «يوم مكتمل»؟ | جميع مهام **خطة ذلك اليوم الفعلية**، دون مهام غير موجودة |
| هل الورد مرتبط بسرعة الحفظ؟ | الورد التقويمي مستقل؛ توقف الحفظ الجديد لا يوقف التلاوة والمراجعة |
| متى تُعلن الختمة؟ | جميع الأثمان محفوظة/موثقة، مع حدث ختمة واحد؛ لا الاكتفاء بمحطة 480 |
| ما الذي يصنع السلسلة؟ | نشاط تعلّم حقيقي؛ لا فتح onboarding أو التنقل أو مجرد التراجع. سياسة الراحة معلنة |
| ماذا يفعل «تثبيت الضعيف»؟ | نشاط مستقل؛ لا يحل محل مراجعة مخططة أكبر منه |
| هل يجوز تصحيح القرآن شخصيًا؟ | الاقتراح يُراجع؛ الأصل لا يتغير بصمت. أي تعديل شخصي موسوم ويمكن إلغاؤه |
| ماذا يعني Reset/Delete؟ | نطاق صريح: هذا الجهاز / كل الأجهزة / الحساب بالكامل، مع منع إعادة إحياء البيانات القديمة |
| ما وعد العمل دون اتصال؟ | التقدم المحلي والمواد المنزّلة فقط؛ الصوت والتذكير الخلفي لهما حدود معلنة |

**المخرج:** صفحة تعريفات قصيرة تستخدمها الواجهة والمتجر والمزامنة والاختبارات. لا تبدأ تطويرًا موازيًا بتعريفات مختلفة.

## 3. الإصدار الأول — «إنجاز صحيح وبيانات محفوظة»

**المدة المقترحة:** أول أسبوعين. \
**الأولوية:** A01–A08 والأمن. \
**المسؤول الأساسي:** المطور، وQA لاختبارات الرجوع.

### المهام

- [x] **T01 — تحديث الحزم المتأثرة بالأمان (A03).** تحديث Next وESLint المتوافقين وتبعيات الصور/البناء، فحص تنبيهات audit الفعلية، ثم lint/type-check/test/build/PWA. لا تستخدم تحديثًا قسريًا غير مراجع.
- [x] **T02 — حواجز فورية للمزامنة (A01).** إيقاف الرفع عند فشل الجلب، ورفع نتيجة الدمج لا لقطة الرندر السابقة، وعدم استبدال الحقول السحابية التي لم تُستعد. إزالة الجدولة الناتجة عن `lastCloudSyncAt` وتنظيف الاشتراك.
- [x] **T03 — حارس ملكية البيانات (A02).** قبل أي دمج/رفع يجب أن يتطابق مالك الحالة مع المستخدم. لا ترفع حالة الحساب السابق إلى الجديد؛ اعرض نقل الضيف كاختيار صريح.
- [x] **T04 — توحيد اكتمال المهام (A04).** دالة بحسب اليوم/الوضع/الخطة، تستخدم في المتجر والدائرة والخطة والإحصائيات والمكافأة والختمة. لا تُكمل مهام غير مطلوبة.
- [x] **T05 — أرقام محفوظ صحيحة (A06).** فصل أبعد محطة عن عدد الأثمان والأجزاء المكتملة؛ تصحيح الخريطة والأوسمة والمشاركة؛ محفوظ سابق لا يختلق حصونًا تاريخية.
- [x] **T06 — فصل التثبيت الحر عن المراجعة المخططة (A07/A18).** صنف مستقل لا يمنح إتمام `review_far` تلقائيًا؛ منع تسجيل إنجاز محطة مستقبلية عبر جلسة المعاينة.
- [x] **T07 — إصلاح السلسلة والسجل (A08).** أفضل سلسلة، أيام مثالية حقيقية، منع تكرار سجل المهمة، وسياسة واضحة للراحة والسلسلة عند انقطاع الأيام.

### اختبارات القبول الملزمة

1. إتمام 4/4 في أول يوم يطابق اكتمال المتجر ومكافأة اليوم والخطة والإحصائيات.
2. أيام 2 و9 و10 و479 و480 تعمل بمقام المهام الصحيح. إتمام آخر ثمن يعلن الختمة مرة واحدة فقط إذا لم توجد فجوات حفظ.
3. استماع واحد في المحطة 16 لا يعطي جزءًا محفوظًا أو حزبين مكتملين.
4. إتمام ثمن ضعيف واحد لا يكمل مراجعة بعيد تضم 16 ثمنًا.
5. فك وإعادة تحديد مهمة لا يضاعف الرصيد أو عدد إنجازاتها اليومية.
6. أفضل سلسلة لا تقل عن الحالية؛ أوسمة الاستمرار تعتمد على سجل صحيح.
7. فشل جلب السحابة لا يتبعه رفع، ولا كتابة كل خمس ثوانٍ أثناء الخمول.
8. مستخدم جديد/محفوظ سابق/ترقية بيانات قديمة لا يفقد الملاحظات أو الحفظ بسبب تصحيح الحسابات.

**بوابة الإصدار:** لا توجد مشكلة معروفة تؤدي إلى خلط حسابين أو الكتابة فوق بيانات سحابية عند فشل الجلب. إذا لم تتحقق، تعطّل الكتابة السحابية المتأثرة مؤقتًا بدل الإعلان عن «مزامنة آمنة»؛ مع إبقاء التصدير والحفظ المحلي متاحين.

## 4. الإصدار الثاني — «مزامنة وترحيل يمكن الوثوق بهما»

**المدة المقترحة:** الأسبوعان 3–4. \
**التبعيات:** تعريفات المنتج وT02/T03/T04. \
**المسؤول:** المطور + QA؛ اختبار Supabase staging بحسابات تجريبية.

### المهام

- [x] **T08 — خدمة مزامنة واحدة.** إزالة اختلاف مسارات الدخول/اليدوية/التلقائية. Snapshot واحد مكتمل ومحقق، وتحويل DTO موحد؛ تشمل الجلسات والإعدادات والتثبيت والختمة ومعلومات التواريخ اللازمة.
- [x] **T09 — تعارضات وحذف قابلان للتتبع.** معرفات ثابتة للجلسات/الإنجازات؛ طوابع/إصدارات للتعديلات؛ سياسة للتراجع والحذف؛ وrevision أو epoch لمنع جهاز قديم من بعث بيانات قبل reset. اشتقاق XP من سجلات فريدة بدل `max` للرصيد.
- [x] **T10 — عزل محلي كامل.** مساحة الضيف وكل حساب، تبادل واضح بينها، وإيقاف/إلغاء المزامنة عند الخروج وتبديل الهوية. لا يكفي `enabled: boolean`.
- [x] **T11 — آلة حالات المزامنة.** محلي / pending / syncing / synced / error، مع dirty revision وإعادة محاولة متدرجة، وعملية واحدة قيد التنفيذ، ومعالجة انقطاع الشبكة. واجهة «متزامن» تأتي من نجاح حفظ لا وجود حساب.
- [x] **T12 — Backup schema وترحيل (A11).** فصل بيانات الحالة عن أفعال Zustand؛ تحقق عميق، إصدارات واضحة للنقل والتخزين، round-trip، حد حجم، معاينة، ونسخة رجوع قبل الاستبدال. تحقّق السحابة عبر schema نفسه.
- [x] **T13 — SQL migrations.** ترحيل آمن للتركيبات الموجودة، لا الاعتماد على `create table if not exists`؛ DTO/types متوافقة، قيود للأرقام، واختبارات RLS.

### اختبارات القبول

- جهاز A يكمل ثمنًا وجهاز B يكمل آخر: لا يضيع أحدهما، ولا تتكرر النقاط.
- ملاحظة قديمة محليًا لا تمحو تعديلًا سحابيًا أحدث بلا قرار واضح.
- حذف ملاحظة/التراجع عن مهمة/reset لا يعود من جهاز قديم عند الاتصال.
- جهاز جديد يستعيد الجلسات والإعدادات ووضع التثبيت وتاريخ الختمة، وليس قائمة المهام فقط.
- ملف مشوه أو نسخة غير مدعومة لا تلمس البيانات الحالية؛ وتُرفض الحقول التي تغطي أفعال المتجر.
- التصدير ثم الاستيراد يحافظان على البيانات لكل الإصدارين الحالي والسابق المدعومين.
- خروج A ودخول B لا يخلط المحفوظ أو الملاحظات أو النقل المنتظر.
- لا يستطيع حساب تجريبي قراءة/تعديل/حذف صف حساب آخر عبر API.

### قرار تقني عملي

لا يلزم بناء CRDT كامل في البداية. استخدم سجلات فريدة وإصدارات وتعارضات محددة، مع تحديثات محمية ومراجعة اختبار جهازين. لكن لا تستبدل المشكلة بدمج OR لكل boolean؛ فهو يمنع التراجع والحذف. الأرقام المشتقة لا تكون مصادر حقيقة متنافسة.

## 5. الإصدار الثالث — «جلسة ومصحف بلا فقد سياق»

**المدة المقترحة:** الأسبوعان 5–6، مع مساحة احتياط عند الحاجة. \
**المسؤول:** المطور للمنطق، المصمم لتخطيط الهاتف، وQA للوصول والأجهزة.

### المهام

- [x] **T14 — مكدس نوافذ موحد (A10/A16).** Dialog من Base UI، طبقة عليا فقط تتعامل مع Escape/Back، focus trap/restore، خلفية inert، وقفل تمرير مركزي. تأكيد إنهاء الجلسة موحد لكل طرق المغادرة.
- [x] **T15 — رأس المصحف وسياقه (A12).** صفان مناسبـان للهاتف، عنوان قصير ومطلع قابل للتوسيع، تعريف صريح للثمن المحدد في الصفحات المشتركة، واتساق الصوت معه. الخطأ في تحميل الصورة لا يبقي spinner بلا نهاية.
- [x] **T16 — وضع التثبيت الحقيقي (A09).** خطة وتاريخ/دورة مستقلان؛ لا إعادة استخدام سجل الثمن 480؛ تقدم إلى الورد التالي، وعدم تغيير عدّ إنجازات الحفظ السابقة. احتفال قابل للتذكر مرة لكل ختمة.
- [x] **T17 — تدفقات الحساب/التصحيح (A13/A14).** كلمة مرور جديدة عند recovery؛ مطابقة عمود التصحيح للمخطط؛ تحقق حدود الآيات وإظهار شروط الإرسال. خيار حذف الحساب عبر جهة خادم آمنة، وتمييزه عن حذف التقدم.
- [x] **T18 — الوصول والتباين.** تصحيح الأسماء والتداخل التفاعلي والـslider؛ أحجام خط ولمس؛ تدقيق الثيمات الخمسة؛ reduced motion؛ وتكبير 200% وقارئ شاشة.

### معايير القبول

1. جلسة نشطة → مصحف → Back يعيد إلى الجلسة دون فقد الوقت أو غلقها؛ ثم Back يعرض التأكيد. إغلاق آخر نافذة يعيد تمرير الصفحة والتركيز.
2. في صفحات 480/481/483 المشتركة يتفق الثمن المحدد والعنوان والصوت، أو تظهر علاقة الصفحة بأكثر من ثمن صراحة.
3. القارئ يعمل في 320/390 بكسل والاتجاهين portrait/landscape دون عمود عنوان طويل أو نص مخفي خلف الصوت.
4. يوم تثبيت جديد يولّد وردًا جديدًا دون محو/إعادة تفسير التاريخ السابق.
5. reset/delete لا تعيد عملية مزامنة قديمة البيانات المحذوفة.
6. رابط الاستعادة ينتهي فعلًا بكلمة مرور قابلة للاستخدام، مع حالات رابط منتهي وغير صالح.
7. في الصفحات المستهدفة لا توجد مخالفات axe حرجة/جسيمة قابلة للإصلاح؛ مع اختبار يدوي لا يستبدله العدد.

## 6. الإصدار الرابع — «يوم واضح وصوت موحد وoffline صادق»

**المدة المقترحة:** الأسبوعان 7–8، والاختبار التجريبي حتى الأسبوع 10 إذا لزم. \
**المسؤول:** تصميم + تطوير + QA.

### المهام

- [x] **T19 — هرمية اليوم.** بطاقة الخطوة التالية فوق الطية، زر أساسي واحد، قائمة مهام مختصرة، ونقل الحديث والإحصائيات الثانوية أسفل الإجراء. عدم إعادة بطاقة الإحصائيات الكبيرة فوق كل تبويب.
- [x] **T20 — تهيئة أقصر.** ثلاث خطوات مفيدة، اختيار محفوظ سابق بالسورة/الجزء مع دقة رقمية وخيار «لاحقًا» للتذكير، دون طلب إذن تلقائي. اجعل وعد المدة تقديريًا بحسب أيام الدراسة.
- [x] **T21 — صوت مشترك (A17).** مسار نشط واحد، MediaSession للنشط فقط، انتقال بين المصحف والجلسة دون تراكب أصوات، وإظهار الخطأ/المحاولة في العرض المختصر. تكرار المقطع في موضع واضح.
- [x] **T22 — خطة وبحث قابلان للاستخدام (A18).** تطبيع الأرقام والتشكيل، فصل معاينة المحتوى عن أقفال الإنجاز، مدى المراجعة الصحيح وترتيب المرور، وعدّ ثابت للجزء رغم الفلترة.
- [x] **T23 — PWA وأداء (A19).** فصل الشاشات الثقيلة، تنزيل اختياري للصور بدل محاولة 72.8 MiB تلقائيًا، إظهار حجم وتقدم وتوفر offline، وخطة cache للهيكل والمواد القريبة مع اختبار cold reopening.
- [x] **T24 — تذكير محلي واضح (A15).** جهة جدولة واحدة مع cleanup، إذن اختياري، نص لا يضمن الإغلاق، واستعمال API المناسب للهاتف. Push الحقيقي خارج هذا الإصدار ما لم يكن أولوية مثبتة.
- [x] **T25 — تثبيت الجودة والتشغيل (A20).** `npm ci`، فحص البيانات وE2E في CI، تحسين بيئة persist tests، وثائق المصدر الفعلي للصوت/الصور، SQL migrations، ومراقبة أخطاء بدون بيانات حساسة.

### معايير القبول

- مستخدم جديد يستطيع العثور على المهمة التالية وبدء جلسة خلال دقيقة، دون إرشاد شفهي؛ الإجراء ظاهر في 390×844 دون تمرير.
- بحث `٢` و`2` يعطي النتائج نفسها، ومعلومات المدى والإجمالي لا تتغير خطأً مع البحث.
- لا يتزامن تشغيل مشغلين؛ شاشة القفل تتحكم بالمقطع النشط، والعودة من القارئ لا تعيد البدء دون اختيار.
- تشغيل offline من إعادة فتح باردة بعد التنزيل، لا فقط استمرار صفحة مفتوحة؛ حفظ التقدم والملاحظات يعمل ثم تُزامَن مرة واحدة عند العودة.
- صورة/صوت غير منزلين لهما حالة مفهومة، ولا تنقطع الجلسة بسبب تحديث SW مفاجئ.
- إيقاف التذكير من أي مسار يمنع مؤقته القديم، ولا يظهر إذن إشعار غير مطلوب.
- تحسن الحزمة الأولية عن خط الأساس **486 KB gzip تجريبي** بنسبة مستهدفة 25–35%، دون كسر وظائف. تُقاس النتيجة بالبناء نفسه ثم على جهاز وشبكة ممثلين.

|---|---|---|
| Memorization | هوية الثمن، محفوظ سابق/مكتسب، حالة الحفظ والتقييم | العدّ الصحيح لا يعتمد على أبعد يوم |
| DailyPlan | تاريخ محلي، نسخة خطة، مهام ومعرفات مواد | لا يتجمد الورد إذا تعثر الحفظ |
| TaskCompletion | معرف مهمة فريد، وقت الإنجاز/التراجع ومالك ونسخة | يمنع تكرار XP ويتيح دمجًا آمنًا |
| Session | معرف ثابت، نوع، مواد، زمن فعلي ووقت وقوعها | دمج جلسات جهازين دون حذف أو تكرار |
| ReviewAttempt | ثمن، تقييم فردي، وقت ومحاولة/جلسة | تاريخ قوة الحفظ بدل آخر علامة فقط |
| MaintenancePlan | طور مستقل وتاريخ/دورة | لا يعيد تعريف إنجازات الرحلة السابقة |
| Settings | إعدادات مع نسخة/وقت تحديث | استعادة صحيحة وتعارض واضح |
| SyncMetadata | userId، schemaVersion، dirty revision، reset epoch | عزل الحساب، منع حلقات الرفع وإحياء المحذوف |

### ضوابط الترحيل

1. يقرأ الترحيل **البيانات فقط** ولا يثق بأفعال مخزنة في JSON.
2. تنشأ نسخة محلية قابلة للاسترجاع قبل الترحيل؛ لا يكتب إلى السحابة قبل النجاح والتحقق.
3. احتفظ بالملاحظات والمواد والتاريخ، ولا تملأ أداء حصون تاريخية لمجرد تحديد محفوظ سابق.
4. لا تعاقب المستخدم بصمت على خطأ XP قديم؛ افصل أي تسوية قديمة موثقة عن نقاط الأحداث الجديدة، أو اعرض التصحيح بوضوح.
5. لا تعِد توزيع كل تاريخ سابق على تقويم غير معروف. ما لا يمكن نسبته لتاريخ صحيح يبقى إنجاز رحلة قديمًا معلوم المصدر.
6. اختبر الترقية والرجوع ومزامنة جهاز لم يُحدَّث بعد، ثم أطلقها على عينة تجريبية صغيرة.

## 8. المزايا اللاحقة — حسب قيمة مثبتة لا حسب كثرة القائمة

بعد تجاوز بوابات الثقة:

### P2-A — ورد مستقل وخطة تعافٍ

- خطة التقويم منفصلة عن سرعة إتقان الثمن، مع ورد مراجعة في أيام التعثر.
- تقدير وقت واقعي، وتعديل الوتيرة من اليوم التالي دون إعادة تفسير مهام منجزة.
- حالات «اليوم للمراجعة» و«لدي 15 دقيقة» لا تعني اختلاق حفظ جديد.

**القبول:** ثلاثة أيام عمل على ثمن واحد تسمح بثلاثة أوراد تقويمية مستقلة، وتحفظ الرقم الحقيقي للمحفوظ.

### P2-B — مراجعة فردية علاجية

- شاشة ثمن واحد في كل خطوة، تقييم ضعيف/جيد/متقن مع تاريخ.
- قائمة تستحق التثبيت بحسب الضعف والوقت منذ آخر مراجعة، ولا تُحصر دائمًا في أول 8 أرقام.
- ابدأ بقواعد بسيطة معتمدة ومفهومة؛ لا تطبق خوارزمية SRS معقدة قبل الحصول على بيانات محاولات جيدة.
- ضع سقف وقت للمراجعة الإضافية، ولا تتلاعب بالخطة المعتمدة دون اختيار المستخدم ومراجعة متخصص.

**القبول:** تقييم عنصر ضعيف لا يغيّر بقية عناصر الجلسة، ويظهر سبب وتوقيت اقتراح مراجعته.

### P2-C — تذكير عند الإغلاق

- Push subscription، توقيت ومنطقة زمنية، جهة جدولة، وإلغاء/حذف اشتراك.
- ميزانية تشغيل ومراقبة تسليم وعدم وعد بتوقيت دقيق مضمون على الهاتف.
- اختبار iOS مثبت وAndroid وإذن مرفوض، وإيقاف التذكير أو حذف الحساب.

**شرط البدء:** مستخدمون حقيقيون يطلبونه أو تظهر البيانات حاجة؛ وإلا تكفي صياغة صادقة للميزة المحلية الحالية.

**مؤجل:** مجتمع/لوحة تنافس، AI لتقييم التلاوة، ملفات عائلية متعددة، أو تقارير كثيرة قبل أن تصبح بيانات التقدم صحيحة.

## 9. استراتيجية الاختبار

### مصفوفة الحد الأدنى

| المستوى | السيناريوهات |
|---|---|
| Unit | مفاتيح مهام الأيام الحدية، اكتمال/تراجع، XP، السلسلة، الأجزاء والأوسمة، قوائم الضعيف |
| Data | كل 480 ثمنًا، مواضع جزئية، حدود السور والأحزاب، صفحات مشتركة ومطالع متوافقة |
| Integration | persist/migrations، backup round-trip، دمج جهازين، error ≠ empty، اختلاف هوية، SQL/DTO |
| E2E | أول جلسة، أول يوم وآخره، محفوظ سابق، تثبيت، session→reader→back، استيراد مع خطأ |
| Accessibility | الثيمات الخمسة، لوحة مفاتيح، تركيز النوافذ، 200% تكبير، قارئ شاشة |
| PWA/device | build إنتاج، تثبيت وتحديث، reopen offline، انقطاع أثناء جلسة، قرب امتلاء التخزين |
| Auth/privacy | recovery، sign-out، A→B، RLS، reset/delete وعدم إحياء المحذوف |
| Audio | اتصال ضعيف/فشل، قارئ متغير، مشغلان، شاشة قفل، خلفية الهاتف، تكرار |

**الأجهزة:** هاتف Android متوسط، iPhone/Safari مثبت وغير مثبت، عرض 320/390 بكسل، ومتصفح مكتبي حديث. السرعة المحلية في sandbox لا تكفي للحكم على تجربة الهاتف.

### بوابات CI المقترحة

`npm ci` → type-check → lint → unit/integration → verify-data → build → E2E على نسخة الإنتاج → تقرير audit وحجم الحزمة.

لا تُعامل كل تحذير أمني كاستغلال متاح، ولا تُخَفِ مخالفات خطرة بمجرد تثبيت حد رقمي مرتفع. وثّق الاستثناء المعلل ومدته ومالكه.

## 10. إطلاق تجريبي ومقاييس النجاح

اختبر الإصدار على **10–15 مستخدمًا** من ثلاث حالات: مبتدئ، لديه محفوظ سابق غير متصل، وحافظ يحتاج تثبيتًا؛ وبينهم شخص يحتاج خطًا أكبر أو يستخدم الهاتف ببطء. هذه عينة لاختبار الاستخدام لا دراسة إحصائية كافية للاحتفاظ.

| المؤشر | هدف مبدئي، يُراجع بعد خط أساس |
|---|---|
| سلامة البيانات | صفر حالات فقد/خلط في مصفوفة الجهازين والحذف والترحيل |
| فهم المهمة | 80% على الأقل يجدون الإجراء التالي دون مساعدة في اختبار الاستخدام |
| بدء أول جلسة | أقل من دقيقة بعد إكمال الاختيارات الأساسية |
| توافق الإنجاز | الدائرة والخطة والإحصائيات وXP تعرض الحقيقة نفسها في كل حالة اختبار |
| المزامنة | تغيير حقيقي واحد/دفعة يزامَن مرة؛ صفر رفع دوري أثناء الخمول |
| المصحف | العودة تحفظ سياق الجلسة، والعنوان والصوت متفقان في كل صفحات الحدود المختبرة |
| الأداء | قياس أولي ثم تحسن حزمة/وقت تفاعل؛ استهداف LCP ≤2.5s وINP ≤200ms وCLS ≤0.1 على قياس ممثل |
| الوصول | لا عوائق حرجة/جسيمة في التدفقات الأساسية + نجاح اختبار يدوي |
| استمرارية الاستخدام | قياس D7/D30 وإكمال ورد الأسبوع بعد توفر بيانات سليمة، لا الادعاء بتحسن دون خط أساس |

لا تجمع نص الملاحظات أو التسجيلات الصوتية لغرض التحليلات. اكتفِ بأحداث عامة ومجمعة مع سياسة خصوصية وموافقة مناسبة.

### خطوات الإطلاق

1. Staging ونسخ بيانات اختبار، ثم تجربة محدودة، ثم نشر تدريجي.
2. مراقبة أخطاء hydration/storage/sync، ومعدل فشل الصوت والصفحات دون بيانات حساسة.
3. حفظ نسخة الحالة السابقة لكل ترحيل، مع مسار رجوع لإصدار التطبيق وبياناته.
4. لا تدفع تحديث SW أثناء جلسة؛ اعرض «تحديث متاح» وخيارًا آمنًا بعد الحفظ.
5. عدم التوسع إذا ظهر فقد بيانات أو خلط حسابات، مهما كان تحسن الشكل.

## 11. أول خمسة أيام عمل — نقطة بدء مباشرة

| اليوم | العمل | المخرج |
|---|---|---|
| 1 | تثبيت التعريفات، مراجعة audit، تسجيل اختبارات فاشلة للأول/الأخير والمزامنة | قائمة قواعد معتمدة + فحوص تعيد إنتاج المشكلات |
| 2 | توحيد مهام اليوم والاكتمال ومكافأة اليوم وقاعدة الختمة | 4/4 و5/5 يطابقان حالة المتجر |
| 3 | المحفوظ الفعلي والسلسلة والأيام المثالية وفصل التثبيت الحر | أرقام وأوسمة غير مضللة |
| 4 | حواجز المزامنة: error/empty، اللقطة المدمجة، منع الحلقة وخلط المالك | لا رفع خطر أو دوري؛ اختبارات نقل وهمي/حسابين staging |
| 5 | تحديث الحزم، تحقق بناء/بيانات/E2E وترحيل أولي، واختبار يدوي هاتف | مرشح إصدار ثقة؛ ما لم يجتز البوابة يبقى غير منشور |

هذه الأيام بداية التنفيذ وليست ادعاء إنجاز النظام كله. إن استغرق ترحيل البيانات أو حماية المزامنة أكثر، يمدد الإصدار الأول وتؤجل الواجهات؛ لا يعكس ترتيب الأولويات.

## الخلاصة

**لا تبدأ بإعادة تصميم التطبيق.** ابدأ بما يجعل عبارة «حفظتُ، راجعتُ، حُفظ تقدمي» صادقة في كل مسار وجهاز. بعد ذلك اجعل الطريق إلى الجلسة أقصر، والمصحف والصوت أكثر اتساقًا، ثم أضف ذكاء المراجعة والتذكير عند ثبوت الحاجة.
